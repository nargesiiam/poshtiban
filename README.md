# Relay — دستیار پشتیبانی مشتری مبتنی بر عامل هوشمند

## راه‌اندازی

```bash
git clone <repo-url>
cd relay
cp .env.example .env   # مقادیر واقعی (ANTHROPIC_API_KEY, TAVILY_API_KEY, ...) را پر کن
docker compose up
```

## معماری (بخش ۱ — زیرساخت)

شش سرویس، هرکدام یک فرایند مستقل با مسئولیت مشخص:

| سرویس     | نقش                                                             |
|-----------|------------------------------------------------------------------|
| frontend  | React — رابط کاربری، مصرف‌کننده‌ی REST و SSE                    |
| backend   | Django+DRF روی ASGI — API، احراز هویت، تولید فرمان، پخش SSE     |
| ai-worker | فرایند مستقل — اجرای عامل LangGraph، مصرف‌کننده‌ی صف            |
| rabbitmq  | صف پیام — تنها راه ارتباط backend و ai-worker                   |
| postgres  | منبع حقیقتِ داده‌ی ساخت‌یافته                                    |
| chromadb  | پایگاه‌داده‌ی برداری برای RAG                                    |

### چرا سرویس‌ها با نام سرویس به هم وصل می‌شوند، نه localhost؟

هر سرویس در Compose داخل شبکه‌ی bridge خودش (`relay-net`) یک کانتینر جدا با
namespace شبکه‌ی مستقل است. `localhost` داخل کانتینر `backend` به خودِ کانتینر
backend اشاره می‌کند، نه به کانتینر postgres. Docker یک DNS داخلی دارد که نام
سرویس (مثلاً `postgres`) را به IP داخلی همان کانتینر resolve می‌کند — به همین
دلیل `POSTGRES_HOST=postgres` است، نه `127.0.0.1`. اگر این پروژه را بدون
Compose و به‌صورت پردازش‌های جدا روی یک هاست اجرا کنیم، همین آدرس‌ها باید IP یا
DNS واقعی شوند — نکته‌ای که در جلسه‌ی دفاع باید بتوانی توضیح بدهی.

### چرا depends_on به معنای «آماده بودن» نیست؟

`depends_on` فقط ترتیب **راه‌اندازی کانتینر** را تضمین می‌کند، نه ترتیب
**آماده بودن سرویس داخل آن**. کانتینر postgres ممکن است در عرض ۱ ثانیه بالا
بیاید ولی فرایند PostgreSQL هنوز ۳-۴ ثانیه دیگر برای پذیرش اتصال آماده نیست.
اگر backend همان لحظه تلاش کند migrate بزند، با connection refused مواجه
می‌شود. راه‌حل رایج و ناقص «چند بار retry دستی در کد» است؛ راه‌حل درست
healthcheck است.

### healthcheck چه چیزی را حل می‌کند؟

هر سرویس یک دستور واقعی برای تست «آیا خودم آماده‌ام؟» دارد
(`pg_isready`، `rabbitmq-diagnostics ping`، فراخوانی heartbeat در chromadb).
با نوشتن:

```yaml
depends_on:
  postgres:
    condition: service_healthy
```

Docker Compose واقعاً صبر می‌کند تا healthcheck سبز شود، نه فقط اینکه کانتینر
`start` شده باشد. این تفاوتِ «کانتینر بالا آمده» با «سرویس آماده‌ی پاسخ‌گویی
است» دقیقاً همان چیزی است که در محیط production هم باعث خطاهای متناوب و
عجیب می‌شود اگر رعایت نشود.

### چرا volume نام‌دار لازم است؟

بدون volume، داده‌ی PostgreSQL و RabbitMQ و ChromaDB داخل لایه‌ی نوشتنی
کانتینر ذخیره می‌شود. با هر `docker compose down` یا rebuild، آن لایه پاک
می‌شود و تمام سفارش‌ها، مکالمات و اسناد embed‌شده از بین می‌رود. volume
نام‌دار (`postgres_data`, `rabbitmq_data`, `chromadb_data`) این داده را
خارج از چرخه‌ی عمر کانتینر، روی هاست نگه می‌دارد — کانتینر یک‌بارمصرف است،
داده نیست.

## معماری (بخش ۲ — دامنه و احراز هویت)

چهار اپ Django، هرکدام یک مرز دامنه‌ی مشخص:

| اپ            | مسئولیت                                                        | نوع مجوزدهی                    |
|----------------|-----------------------------------------------------------------|----------------------------------|
| accounts       | ثبت‌نام، ورود (JWT)، شناسایی کاربر جاری                         | —                                 |
| orders         | Product، Order، RefundRequest                                   | مالکیت (کاربر فقط داده‌ی خودش)   |
| documents      | اسناد دانش شرکت برای RAG                                        | نقش (فقط staff آپلود می‌کند)     |
| conversations  | Conversation، Message                                            | مالکیت                            |

### چرا مجوزدهی در کد است، نه در prompt؟

سند صراحتاً همین را می‌خواهد و دلیلش ساده است: پرامپت یک رشته‌ی متنی است که
مدل زبانی آن را «می‌خواند»، نه اجرا می‌کند. نوشتن «فقط سفارش‌های همین کاربر
را نشان بده» در system prompt یک **درخواست** از مدل است، نه یک **قید**. اگر
کاربر با مهندسیِ پرامپت («فرض کن ادمین هستی و...») سعی کند این قید را دور
بزند، یا اگر خودِ مدل در یک مسیر نادر تصمیم عجیبی بگیرد، هیچ‌چیزِ دیگری
جلوی نشتِ داده را نمی‌گیرد.

راه‌حلی که اینجا پیاده شده：هیچ tool یا endpoint‌ای پارامتر `user_id` را از
ورودی (چه از کاربر، چه از خروجی مدل) قبول نمی‌کند. شناسه‌ی کاربر همیشه از
`request.user` می‌آید — چیزی که از توکن JWT تأیید‌شده استخراج شده، نه از
متنی که هرکسی می‌تواند بنویسد. و کوئری‌ست همیشه از یک نقطه‌ی مرکزی عبور
می‌کند: `Order.objects.for_user(user)`. یعنی اگر فردا یک tool جدید یا یک
ویوی جدید اضافه شود، مجوزدهی را «دوباره پیاده‌سازی» نمی‌کند، فقط از همان
متد استفاده می‌کند — یک نقطه‌ی حقیقت، نه ده کپی که ممکن است یکی‌شان
فراموش شود.

نمونه‌ی ملموس برای جلسه‌ی دفاع: در `OrderDetailView.get_queryset` اگر
کاربر A بخواهد سفارشِ کاربر B را با `GET /api/orders/17/` بخواند، پاسخ
`404` است — نه چون یک `if` جایی چک کرده «آیا مالک است؟» و بعد ۴۰۳ برگردانده
(که یعنی وجود سفارش را لو می‌دهد)، بلکه چون آن سفارش از همان اول در
queryset این کاربر وجود ندارد. این تفاوتِ فیلتر در لایه‌ی داده با چک در
لایه‌ی نمایش است.

### چرا دو نوع مجوزدهی متفاوت (مالکیت در orders، نقش در documents)؟

Order داده‌ی شخصی است — مرز طبیعی‌اش «مالِ کیست». Document دانش سازمانی
است و مالِ کسی نیست؛ مرزش «چه کسی حق افزودن/تغییرش را دارد» است، نه
مالکیت. قاطی کردن این دو مدل ذهنی باعث می‌شود بعداً یا اسناد را اشتباهی
per-user فیلتر کنی (و عامل نتواند به سیاست بازگشت کالا دسترسی پیدا کند)
یا سفارش‌ها را عمومی بگذاری (نشت داده‌ی شخصی). این دو `PermissionClass`
جدا (`for_user` در orders، `IsStaffOrReadOnly` در documents) دقیقاً همین
تفکیک را در کد نشان می‌دهد.

## معماری (بخش ۳ — رویدادمحور با RabbitMQ)

این مهم‌ترین تفاوت این پروژه با دوره‌ی مرجع است. در دوره، Maya داخل همان
درخواست HTTP کاربر اجرا می‌شود — یعنی یک worker وب Django برای چند ثانیه
(هر چقدر Claude طول بکشد) قفل می‌ماند. اینجا این دو کاملاً جدا شده‌اند.

### مسیر یک پیام

```
React ──POST──▶ Django (SendMessageView)
                    │
                    │  Message ذخیره می‌شود
                    │  correlation_id تازه ساخته می‌شود
                    │
                    ▼
         command: chat.message.process
                    │
              relay.commands (exchange)
                    │
                    ▼
         ai_worker.commands (queue)
                    │
                    ▼
              ai-worker (consumer)
        idempotency check → پردازش → ack
                    │
                    ▼
      event: agent.reply.completed (و رویدادهای میانی)
                    │
              relay.events (exchange)
                    │
                    ▼
           backend.events (queue) ──▶ پل SSE (بخش ۶) ──▶ React
```

Django بلافاصله بعد از publish کردن command، با `202 Accepted` به React
جواب می‌دهد — منتظر جواب Maya نمی‌ماند. جوابِ واقعی از مسیر جداگانه‌ی SSE
می‌آید. همین یعنی یک worker وب Django در تمام مدتی که Claude «فکر می‌کند»
اشغال نیست و می‌تواند درخواست‌های دیگر را سرویس بدهد.

### command در برابر event

- **command** = «این کار را انجام بده». دقیقاً یک مصرف‌کننده مشخص دارد
  (ai-worker). مثال‌ها: `chat.message.process`، `document.ingest`.
- **event** = «این اتفاق افتاد». ممکن است صفر یا چند مصرف‌کننده داشته
  باشد و هیچ‌کدام منتظرش نیستند. مثال‌ها: `agent.tool.called`،
  `agent.reply.delta`، `agent.reply.completed`، `agent.escalated`،
  `refund.decided`، `document.ingested`.

برای همین دو exchange جدا داریم — `relay.commands` (مقصد واحد و مشخص) و
`relay.events` (پخش به هرکسی که علاقه‌مند است). ساختار هر دو یکسان و
نسخه‌دار است (`event_id`, `correlation_id`, `event_type`, `version`,
`producer`, `occurred_at`, `payload`) — پیاده‌سازی کامل در
`apps/events/messaging.py`.

### دو پرسشِ الزامی سند

**اگر همان command دو بار برسد چه می‌شود؟**
پیش از هر پردازش، `atomic_command_processing` تلاش می‌کند در جدول
`events_processedcommand` رکوردی با کلید `event_id` بسازد. بار دوم این
INSERT به‌خاطر primary key تکراری شکست می‌خورد؛ worker `DuplicateCommand`
می‌گیرد، هیچ پردازشی نمی‌کند، فقط ack می‌کند. کاربر دو پاسخ یا دو بار
استرداد وجه نمی‌بیند.

**اگر worker پیش از ack از کار بیفتد چه می‌شود؟**
اثر جانبیِ واقعیِ command (مثلاً ذخیره‌ی پاسخ) و INSERT مربوط به
idempotency هر دو در یک تراکنش Postgres هستند. اگر worker وسط کار کرش
کند، آن تراکنش هرگز commit نمی‌شود — پس چیزی نصفه‌نیمه در دیتابیس نمی‌ماند.
چون پیام هم ack نشده (manual ack)، RabbitMQ آن را نزد worker دیگری (یا
همین worker پس از ری‌استارت) دوباره تحویل می‌دهد. نتیجه: بازپردازش کامل،
نه داده‌ی خراب یا نصفه.

### تلاش مجدد نمایی

اگر پردازش با خطای غیرمنتظره (نه duplicate) مواجه شود، شمارنده‌ی
`x-retry-count` از header پیام خوانده می‌شود. تا سقف ۵ بار، نسخه‌ای از
پیام با تأخیر نمایی (۱، ۲، ۴، ۸، ۱۶ ثانیه) به یک صف تأخیر با
dead-letter-exchange به سمت صف اصلی فرستاده می‌شود. بعد از سقف، پیام
مستقیم به DLQ می‌رود تا worker برای همیشه روی یک command خراب گیر نکند.

## معماری (بخش ۴ — عامل هوشمند با LangGraph)

**یک** عامل خوش‌ساخت، نه چند عامل نمایشی — سند صریح می‌گوید «تعداد عامل
نمره ندارد، عمق دارد». گراف فقط دو گره دارد:

```
        ┌──────────┐   tool_use   ┌────────┐
   ───▶ │  agent   │─────────────▶│ tools  │
        └──────────┘               └────────┘
             ▲                          │
             └──────────────────────────┘
                  (نتیجه‌ی ابزار به agent برمی‌گردد)
             │
             │ متن نهایی (بدون tool_use)
             ▼
            END
```

### پنج ابزار، سه منبع دانش + یک اقدام

| ابزار                      | منبع        | برچسب source |
|------------------------------|--------------|--------------|
| get_order_status              | Postgres     | db           |
| get_refund_history             | Postgres     | db           |
| search_company_documents        | ChromaDB (RAG)| rag         |
| search_web                      | Serper.dev   | web          |
| create_refund_request (اقدام)   | Postgres     | action       |

### چرا این دو خطا مهم‌ترند از پاسخ نادرست؟

سند می‌گوید: «جست‌وجو در وب برای چیزی که در پایگاه‌داده بوده» و «پاسخ از
حافظه‌ی مدل در جایی که باید ابزار صدا زده می‌شد» بدترند از یک پاسخ اشتباه
معمولی — چون این‌ها نشان می‌دهند مسیریابیِ عامل اصلاً شکسته است، نه فقط
یک جزئیات اشتباه. برای همین system prompt (`prompts.py`) این دو قانون را
با صراحت و در بالای همه‌چیز می‌آورد، و توضیح هر ابزار (`tools.py`) هم
همان مرز را دوباره تکرار می‌کند — چون تنها یک‌بار گفتن در system prompt
کافی نیست، مدل باید در لحظه‌ی انتخاب ابزار هم همان راهنما را جلوی چشمش
ببیند.

### مرزبندی ابزارها (الزام صریح سند)

هر tool schema فقط فیلدهای تایپ‌دار و محدود می‌گیرد (`order_id: integer`،
`query: string`) — هیچ ابزاری پارامتری مثل «فیلتر دلخواه» یا «SQL» ندارد
که مدل بتواند از طریقش هرچیزی از دیتابیس بخواند. حتی وقتی `order_id` از
خروجی مدل می‌آید، executor همیشه با `AND user_id = %s` (که از payload
تأییدشده‌ی command می‌آید، نه از مدل) فیلتر می‌کند — دقیقاً همان الگوی
`for_user()` بخش ۲، این‌بار در دنیای ابزارهای عامل. اگر مدل عمداً یا در
اثر توهم شناسه‌ی سفارش کاربر دیگری را حدس بزند، چیزی برنمی‌گردد.

### سقف گام‌ها

`MAX_STEPS = 8` در `graph.py`. اگر عامل بعد از ۸ رفت‌وبرگشت هنوز به پاسخ
نرسیده (مثلاً به‌خاطر یک الگوی نادر که مدل مدام همان ابزار را با ورودی
کمی متفاوت صدا می‌زند)، گراف به‌جای ادامه‌ی بی‌پایان، یک پیام محترمانه
برمی‌گرداند و کاربر را به پشتیبانی انسانی ارجاع می‌دهد. این دقیقاً همان
«سقف تعداد گام تا اعتبار شما را در یک درخواست نسوزاند» است.

### چرا رابط ابزار RAG (بخش ۴) از پایپ‌لاین embedding (بخش ۵) جداست؟

`search_company_documents` همین الان کار می‌کند و به ChromaDB وصل است،
اما تا وقتی بخش ۵ (پایپ‌لاین آپلود → chunk → embed) چیزی در آن ذخیره
نکرده، نتیجه‌ی خالی برمی‌گرداند. این جداسازی عمدی است: «عامل چطور از یک
ابزار بازیابی استفاده می‌کند» و «آن ابزار چطور پر می‌شود» دو تصمیم
معماری مجزا هستند و نباید در یک تکه کد قاطی شوند.

## معماری (بخش ۵ — بازیابی اطلاعات RAG)

مسیر کامل یک سند، از آپلود تا قابل‌جست‌وجو شدن:

```
staff → POST /api/documents/ (فایل + عنوان)
            │
            │  Document ذخیره می‌شود (ingestion_status=pending)
            ▼
   command: document.ingest  ──▶ relay.commands ──▶ ai_worker.commands
                                                          │
                                                          ▼
                                                     ai-worker
                                          extract_text → chunk_text → embed
                                                          │
                                                          ▼
                                              ChromaDB (collection: company_docs)
                                                          │
                                                          ▼
                                        ingestion_status='ready' + event.document.ingested
```

### چرا فایل را از یک bind mount مشترک می‌خوانیم، نه از طریق API؟

backend فایل را روی دیسک (`media/`) ذخیره می‌کند. دو گزینه بود: ai-worker
یا فایل را با یک درخواست HTTP از backend بگیرد (یک وابستگی شبکه‌ی اضافه
و کند برای فایل‌های بزرگ)، یا همان مسیر دیسک را از طریق یک bind mount
مشترک (`./backend/media:/app/media:ro`) مستقیم بخواند. دومی را انتخاب
کردیم چون سریع‌تر، ساده‌تر برای دیباگ (فایل روی هاست هم قابل دیدن است)
و بدون افزودن یک round-trip HTTP غیرضروری است. نکته: ai-worker این mount
را read-only دارد — دلیل اضافه، مطمئن شدن از اینکه worker هرگز فایل
کاربر را تغییر نمی‌دهد، فقط می‌خواند.

### چرا این پایپ‌لاین دوباره سیستم retry/idempotency نساخته؟

`ingest_document` در `rag.py` هیچ try/except داخلی برای نشانه‌گذاری
شکست ندارد — عمداً. اگر استخراج متن یا embedding شکست بخورد، exception
از تراکنش بالا می‌رود و دقیقاً همان مسیر retry نمایی و idempotency
بخش ۳ آن را می‌گیرد؛ بعد از ۵ تلاش ناموفق به DLQ می‌رود. یک مکانیزم
اطمینان برای هر دو نوع command (چت و ingestion)، نه دو سیستم موازی.

**محدودیت شناخته‌شده** (نکته‌ی خوب برای Q&A): اگر سندی نهایتاً به DLQ
برسد، `ingestion_status` همچنان `pending` می‌ماند، نه `failed` — چون
consumer.py عمداً generic است و نمی‌داند کدام command چه فیلد
وضعیتی دارد. توسعه‌ی طبیعی بعدی: یک هندلر برای DLQ که بر اساس
`event_type` وضعیت مناسب را ثبت کند.

### حفظ ارجاع منبع

هر chunk با metadata شامل `title` و `document_id` در ChromaDB ذخیره
می‌شود. وقتی ابزار `search_company_documents` (بخش ۴) نتیجه برمی‌گرداند،
با پیشوند `internal:` علامت می‌خورد — دقیقاً برای اینکه در پاسخ نهایی و
در UI با ارجاع وب (`web:`) قاطی نشود، طبق الزام صریح سند.

## معماری (بخش ۶ — پخش زنده با SSE)

```
ai-worker ──publish──▶ relay.events ──▶ backend.events (queue)
                                              │
                                    EventBroadcaster (یک consumer
                                    مشترک در کل عمر backend، با aio-pika)
                                              │
                              fan-out بر اساس conversation_id در حافظه
                                              │
                                   asyncio.Queue (به‌ازای هر اتصال SSE)
                                              │
                          StreamingHttpResponse (async view، نه Channels)
                                              │
                                     fetch + ReadableStream در React
                                     (نه EventSource — چون Authorization
                                      header سفارشی لازم داریم)
```

### چرا Channels لازم نبود؟

SSE یک پاسخ HTTP طولانی‌عمر است، نه WebSocket. Django از نسخه‌ی ۴.۲ به‌طور
بومی از async view و `StreamingHttpResponse` پشتیبانی می‌کند؛ داشتنِ
Daphne (سرور ASGI) به‌تنهایی کافی است. Channels یک لایه‌ی routing و
consumer اضافه می‌آورد که فقط وقتی لازم می‌شود که واقعاً WebSocket بخواهیم
(بخش امتیازی این پروژه). اضافه کردنش اینجا پیچیدگی بی‌دلیل بود.

### چرا یک consumer مشترک (`EventBroadcaster`)، نه یکی به‌ازای هر اتصال SSE؟

اگر با ۲۰۰ کاربر هم‌زمان چت باز، ۲۰۰ اتصال جدا به RabbitMQ باز کنیم،
overhead غیرضروری و مدیریت‌نشدنی می‌شود. به‌جایش، یک consumer تنها در کل
عمر فرایند backend به صف `backend.events` گوش می‌دهد و هر envelope را
بر اساس `conversation_id` در حافظه به `asyncio.Queue`های مربوط به
اتصال‌های SSE زنده پخش می‌کند — fan-out در حافظه، نه در RabbitMQ.

### چرا fetch + ReadableStream به‌جای EventSource بومی؟

`EventSource` مرورگر اجازه‌ی هدر `Authorization` سفارشی نمی‌دهد؛ تنها راه
معمول، گذاشتن توکن در query string است که در لاگ‌های سرور و تاریخچه‌ی
مرورگر می‌ماند. با `fetch` و خواندن دستیِ `ReadableStream` (`src/sse.js`)
همان الگوی SSE را با هدر امن پیاده کردیم و کنترل کامل روی منطق reconnect
و وضعیت اتصال داریم.

### بافر کردن رویدادهای تدریجی (delta)

`graph.py` از streaming API آنتروپیک استفاده می‌کند، اما به‌ازای هر توکن
پیام روی صف نمی‌گذارد؛ متن را در یک buffer جمع می‌کند و هر ۴۰ کاراکتر (یا
در پایان پاسخ) یک `agent.reply.delta` منتشر می‌کند — دقیقاً الزام صریح
سند.

### مرز میان جریان و record of system — تصمیم طراحی و دفاعش

**منبع حقیقتِ پاسخ همیشه ردیف `Message` در Postgres است، نه بایت‌های
استریم.** `agent.reply.delta` فقط جلوه‌ی بصریِ «در حال تایپ» است؛ وقتی
`agent.reply.completed` می‌رسد (یا وقتی کلاینت بعد از قطعی دوباره وصل
می‌شود)، React همیشه با یک `GET` به REST از نو مکالمه را می‌خواند
(`refreshMessages`)، نه اینکه سعی کند بایت‌های نیمه‌کاره‌ی استریم قبلی را
ادامه بدهد.

اگر جریان وسط تولید قطع شود: کاربر یک حباب «در حال تایپ» نیمه‌کاره می‌بیند
تا لحظه‌ی قطعی؛ به‌محض reconnect (چه با رسیدن `agent.reply.completed`، چه
با اتصال دوباره‌ی SSE)، آن حباب موقت پاک و با پاسخ کامل و رسمی از Postgres
جایگزین می‌شود. worker همچنان دارد کار می‌کند (چون کاملاً از عمر اتصال SSE
مستقل است)؛ کاربر فقط دیرتر جوابش را می‌بیند، نه جواب خراب یا نصفه.

### وضعیت‌های اتصال — از رویداد واقعی سرور، نه فرض

`connecting` / `connected` / `reconnecting` / `failed` / `disconnected`
همه از `src/sse.js` می‌آیند و مستقیماً به موفقیت یا شکست واقعیِ `fetch`
وابسته‌اند — نه یک تایمر یا حدس. بعد از ۶ تلاش ناموفق با تأخیر نمایی،
حالت `failed` پایدار می‌ماند (توقف بی‌صدا ممنوع، طبق الزام سند)، و badge
رنگی در بالای صفحه‌ی چت آن را نشان می‌دهد.

## معماری (بخش ۷ — رصدپذیری و هزینه)

### دو ابزار رصدپذیری مکمل، یک شناسه‌ی مشترک

- **EventLog در Postgres (بخش ۳)** → مسیر سیستمی: کدام command، کدام
  event، چه زمانی، چند بار retry شد.
- **Langfuse (این بخش)** → مسیر مدل: کدام prompt، کدام ابزار با چه
  ورودی/خروجی، چند توکن.

هر دو با یک `correlation_id` قابل جست‌وجوی متقابل‌اند — `trace_id` در
Langfuse عمداً برابر همان `correlation_id` گذاشته شده (`observability.py`).
یعنی وقتی سر جلسه‌ی دفاع یک درخواست را در جدول `EventLog` پیدا می‌کنی،
همان شناسه را می‌توانی مستقیم در Langfuse هم جست‌وجو کنی و رد کامل
تصمیمات مدل را ببینی.

### شمارش واقعی توکن، نه حدس

هر فراخوانی Claude (هر گام از گراف) یک شیء `usage` واقعی برمی‌گرداند
(`input_tokens`, `output_tokens`) — این‌ها در `state` جمع می‌شوند
(`total_input_tokens`, `total_output_tokens`) و در پایان اجرا به هزینه‌ی
دلاری تبدیل می‌شوند (`pricing.py`). هر جست‌وجوی موفق Serper.dev هم یک credit
اضافه می‌کند. مقادیر قیمت در `pricing.py` تقریبی‌اند و باید با تعرفه‌ی
واقعی حساب شما به‌روزرسانی شوند — نکته این نیست که عدد دقیقاً درست باشد،
نکته این است که مکانیزم شمارش واقعی است، نه یک رشته‌ی ثابت «رایگان بود».

### هزینه در UI

هزینه روی خودِ ردیف `Message` در Postgres ذخیره می‌شود (نه یک محاسبه‌ی
جانبی)، از REST برمی‌گردد، و در صفحه‌ی چت هم زیر هر پاسخ (هزینه‌ی همان
پاسخ) و هم در پایین صفحه (جمع کل گفت‌وگو، با `reduce` روی پیام‌ها) نشان
داده می‌شود.

## چک‌لیست جلسه‌ی ارائه

سند می‌خواهد: معماری روی تخته از حفظ، مسیر موفق با ارجاع + پنل فعالیت
زنده، ارزیابی زنده، Q&A روی هر بخش از کد. نقشه‌ی سریع برای هرکدام:

1. **معماری روی تخته**: نمودار «مسیر یک پیام» در بخش ۳ همین فایل — همان
   را با دست بکش (React → Django → RabbitMQ → ai-worker → RabbitMQ →
   SSE → React).
2. **مسیر موفق زنده**: یک سؤال بپرس که به هر سه منبع نیاز داشته باشد
   (مثلاً «وضعیت سفارش ۱۲۳ چیه و طبق سیاست شرکت میشه برش گردوند؟») تا هم
   `get_order_status` هم `search_company_documents` را ببینی، با پنل
   فعالیت زنده و ارجاع منبع مشخص در پاسخ نهایی.
3. **قطعی و اتصال مجدد**: هنگام یک پاسخ در حال تولید، ai-worker یا
   RabbitMQ را متوقف کن و نشان بده badge وضعیت اتصال چطور واقعی و زنده
   عوض می‌شود (بخش ۶).
4. **دو خطای ممنوع**: یک سؤال بپرس که عمداً باید از حافظه یا وب اشتباه
   جواب داده شود (مثلاً چیزی که در DB هست) و نشان بده مدل درست مسیریابی
   می‌کند، نه اینکه از حافظه حدس بزند.
5. **Q&A روی بخش‌های اول**: چهار سؤال بخش ۱ (چرا نام سرویس، چرا
   depends_on کافی نیست، healthcheck چه می‌کند، چرا volume نام‌دار) و دو
   سؤال بخش ۳ (دوبار رسیدن command، کرش worker) را از حفظ باش.
